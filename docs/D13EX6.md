# D13EX6 — Protected Routes, Backend Authorization, and Client-Side Manipulation

## Interview Question

> A React application protects sensitive routes using `ProtectedRoute` and only displays admin actions when `user.role === "admin"`. Is the application secure against unauthorized access? If not, how can these protections be bypassed, and what must the backend enforce?

## Answer

**No. `ProtectedRoute` and role-based conditional rendering improve navigation and user experience, but they are not security boundaries.** Both rely on client-side state or props, which the user can inspect or manipulate in their own browser. An attacker can also bypass the React UI entirely and send HTTP requests directly to the API.

The **backend must independently authenticate each protected request and authorize the requested action against the specific resource**. For example, an authenticated user might be allowed to read a task but not promote another user or delete a task they do not own. A request without valid authentication typically receives **401 Unauthorized**; a request from an authenticated user who lacks permission typically receives **403 Forbidden**.

**Key distinction:** Authentication establishes who the user is; authorization establishes what that user can do. UI restrictions do not replace either server-side check.

## TaskFlow Example: The `Promote User` Button

In TaskFlow, the authenticated user is stored in React state in `App.tsx`:

```tsx
const [user, setUser] = useState<AuthUser | null>(null);
```

`AppRoutes` passes the user's role to `UsersPage`:

```tsx
<Route path={routePaths.users} element={<UsersPage role={user?.role} />} />
```

`UsersPage` derives whether to display the admin action:

```tsx
const isAdmin = role === "admin";

return (
  <Section title="Users">
    {isAdmin && (
      <button type="button" onClick={handlePromoteUser}>
        Promote User
      </button>
    )}
    {/* Existing user content */}
  </Section>
);
```

This is appropriate **role-based UI**, but it is not authorization enforcement.

## Client-Side Manipulation Demonstration

**Purpose:** Demonstrate, in the local TaskFlow development app, that displaying a protected UI control is not proof of having backend permissions.

1. For the demonstration, sign in with a mock user whose `role` is `"user"`, and navigate to `/users`. The `Promote User` button should be hidden.
2. Open **React Developer Tools → Components** and select `App`.
3. If the installed DevTools version supports editing Hook state, locate the `user` state and change its `role` from `"user"` to `"admin"`.
4. React updates the affected components. `AppRoutes` passes `role="admin"` to `UsersPage`; `isAdmin` becomes `true`; the real React `Promote User` button is rendered.

**What this proves:** The role used for client-side rendering can be manipulated locally. It does **not** prove that the user's identity or permissions have changed on the backend.

### Why not simply call `setUser()` in the browser console?

`setUser` is a function scoped to the `App` component and is **not** exposed globally. Typing `setUser(...)` in a normal browser console usually produces a `ReferenceError`. React DevTools can interact with React renderer internals to inspect and, where supported, edit Hook state without a globally accessible setter.

### DOM injection is a different demonstration

A user can also append a visual button in the console:

```js
const button = document.createElement("button");
button.textContent = "Promote User";
document.body.appendChild(button);
```

However, this is **not** the React button: it does not receive `onClick={handlePromoteUser}`. Adding a DOM element is not equivalent to modifying React state or gaining authorization.

### Scope of the local TaskFlow demo

At this stage, `handlePromoteUser` only updates local React state (the displayed user's professional role). It does **not** call a protected backend endpoint. Therefore, this exercise illustrates the weakness of client-side UI checks; it is **not** an actual server authorization bypass. The walkthrough is a demonstration procedure, not a claim that all DevTools environments support the same editing controls.

## What a Secure Backend Must Do

If TaskFlow later exposes a promotion endpoint, for example:

```http
PATCH /api/users/123/role
Authorization: Bearer <access_token>
Content-Type: application/json

{"role":"admin"}
```

The backend must:

1. Verify the supplied session or token and establish the user's identity.
2. Check that the authenticated user has permission to promote users.
3. Check any resource-specific and business-policy restrictions before changing user `123`.
4. Reject unauthorized requests regardless of whether the frontend displayed the button.
5. Return an appropriate status (`401` for invalid/missing authentication, `403` for insufficient permission).

**Production rule:** Never trust `user.role`, `isAdmin`, hidden buttons, or `ProtectedRoute` as evidence of authorization. Only the backend can enforce protected operations and control access to sensitive data.

## Relevant Design Concepts

- **Single Source of Truth:** `App` owns the UI authentication state; children receive values through props.
- **Derived Value:** `isAdmin` is calculated from `role` and does not need separate React state.
- **Guard Pattern:** `ProtectedRoute` controls navigation to protected UI routes.
- **Defense in Depth:** Use frontend restrictions for UX alongside independent backend authorization for actual security.

## Exercise Outcome
